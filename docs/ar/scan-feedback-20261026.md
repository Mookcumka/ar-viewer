# Единый сценарий чтения AR-листа: обратная связь

26.10.2026. Основа: AR72 b3b05cf, опубликованный ar-viewer6/main f9758a0. Пользователь сообщил: неясно расстояние и какие части считаны; принтера нет, экран ноутбука имитирует бумагу. Владелец отклонил отдельный «режим ноутбука»/перелистывание. Согласован один лист/одна камера, QR в любом порядке. Эта доработка относится к viewer, EXE/Exporto/геометрия/протокол не меняются.

## Интерфейс и состояния

- После первого валидного пакета виден ряд номеров 1…N с отметками «принят/ожидается», точный список оставшихся номеров. N берётся из пакета; для QRL2 допускается каждый count1…6. Индекс wire0 становится UI1.
- Каждое новое принятие явно подтверждается. Повтор не увеличивает счётчик; спокойное «QR N уже считан» ограничено по частоте и не вытесняет свежее подтверждение. У принятого блока данные ещё не обязательно прошли проверку всей сцены.
- Контур соответствует только успешно декодированному кадру и результату приёма. Зелёный — принят/уже принят; янтарный — старый заблокированный лист/ошибка. Неподдерживаемый/повреждённый пакет не получает зелёного подтверждения. Несколько контуров могут кратко сосуществовать. TTL750мс, после900мс старый кадр уже не рисуется. Это НЕ pose/world anchor и не отслеживание QR после чтения.
- Состояния: сборка частей → все части получены/проверка SHA и восстановление → модель готова → существующий rel=ar Quick Look. Готовность объявляется после декодирования и записи USDZ, не по одному счётчику. После готовности QRL сканирующий interval остановлен; камера/AR.js не пересоздаются. «Новый лист» очищает модель/прогресс/контуры и возобновляет сканирование при активной камере. Прежний hash остаётся заблокирован по прежнему контракту New Sheet; для повторного открытия того же файла есть явный HTML import.
- Legacy Hiro/AR1/4/5 продолжает прежний marker loop. Для перехода с готового QRL к новому листу теперь явно используется New Sheet; тест смешанного потока учитывает это согласованное изменение. Трекинг/калибровка/сглаживание не переписаны.
- Статическая инструкция: QR целиком с белым полем, задержать телефон, порядок любой. При долгом отсутствии результата — направиться на непринятый код, при видимом размытии вблизи отодвинуть телефон. UI не объявляет выдуманное расстояние/резкость/блик по отсутствию decode. Точные сантиметры Safari здесь не измеряет.
- «Открыть HTML» доступно в обычном интерфейсе. Читаются только data-packet, HTML не выполняется. Отчёт отличает html-file от camera; этот путь не доказывает оптическое чтение.
- Опциональный звук включается только явной кнопкой/жестом пользователя: короткий сигнал новой части, двойной готовности, дубликаты молчат. Без поддержки/доступа остаётся визуальный feedback. Вибрация Safari не обещается.

## Сканирование одного листа

Используется тот же video AR.js/getUserMedia, до1280px ширины кадра. Новый scan-feedback.js не получает геометрию и не владеет камерой. jsQR возвращает один код; helper после decode маскирует только его четырёхугольник в копии текущего кадра и продолжает поиск. Дубликаты, launch URL и чужие коды тоже не мешают поиску следующих. AABB не используется: на повёрнутом листе она могла бы закрыть соседний QR.

План поиска содержит12областей: весь кадр и перекрывающиеся области3×2,2×2,центр. Если jsQR теряется среди множества finder patterns, области позволяют выделить отдельные коды; это координаты поиска внутри того же листа, не специальная компоновка листа и не отдельный режим. На фиксированном тестовом листе проверяются launch+6частей. В каждом snapshot выполняется максимум3decode: сначала весь кадр, затем2из11ROI с циклическим сдвигом между свежими кадрами. Поэтому приближённый код проверяется всем кадром сразу, без ожидания его очереди ROI. Поэтому full/ROI не обрабатываются все подряд на каждом frame. Miss тоже возвращает управление: пустой кадр не может выполнить все попытки внутри одного next(). Caller принимает результаты последовательно, отдаёт управление UI между вызовами и проверяет scanBatch/cameraEpoch ДО следующего вызова и ПОСЛЕ await. Stop/New Sheet/resize/background отменяют хвост старого кадра. Маска не переносится на новый кадр. Чужой hash отклоняет прежний Collector, не сбрасывая текущую сборку.

Это bounded число вызовов (3накадр), НЕ жёсткий CPU budget: один jsQR не прерывается.900мс относятся только к свежести контуров. Время/нагрев iPhone ещё требуется измерить; полный лист с мелкими кодами не гарантируется читаемым одновременно. По-прежнему можно приблизить камеру к любому непринятому коду того же неподвижного листа.

## Координаты, lifecycle и поставка

jsQR corners переводятся из декодируемого кадра через фактический video.getBoundingClientRect в CSS координаты SVG. Текущий AR.js сам задаёт aspect-preserving размеры/отрицательные margins: для fill повторного cover нет. Для object-fit cover/contain учитывается центральная обрезка/letterbox. Overlay pointer-events:none; resize/pause/reset очищают контуры. DPR повторно не применяется.

Root offline cache повышен до v9; scan-feedback.js обязательный ресурс. Прежний v8 не объявляется готовым новой версией UI. Portable bundle включает helper, не включает test vectors/кадры. Публикация public copy требует отдельного разрешения; без него изменения только Draft.

Журнал хранит ограниченные события приёма, camera width/height/frameRate/facingMode, время до принятия частей, счётчики кадров/прочитанных/повторных/отклонённых пакетов. Нет deviceId, кадров или геометрии; scan counters относятся к текущему явному сеансу/New Sheet, не к физическому качеству AR.

## Проверки и приёмка

Unit: N1…6/duplicates/missing; mapping negative margins и cover/contain; quadrilateral mask; лимит и отмена generator. Browser: прежние протоколы/HTML/cache/races/Hiro плюс один НЕПОДВИЖНЫЙ лист с launch+6data QR, первая часть3 и её повтор, камера затем приближается к разным областям того же листа (коды на листе не меняются), наклонённый QR и разные размеры viewport. Synthetic C# vectors — только тесты; не доказательство экспорта Revit или камеры iPhone.

Ручная приёмка владельцем: тот же реальный HTML квартиры на экране, без перелистывания кодов; пользователь сам понимает принятые/оставшиеся части, читает их в любом порядке и видит готовность после SHA. Сохранить viewer JSON и запись экрана iPhone; проверить portrait/landscape, New Sheet, Stop/resume, HTML fallback и Quick Look. Затем бумага при доступном принтере. Зафиксировать время до первого QR/полной сборки/дубликаты/фактическое разрешение. Не считать AR подтверждённым по кнопке или software tests.

### Ограничение оптики, выявленное при разработке

На одном snapshot1280×960 с плотными QRv24 по2–3px/module whole-frame jsQR находил launch или только часть data QR; перекрывающиеся ROI улучшили результат, но НЕ обеспечили уверенное одновременное чтение всех7кодов, особенно при наклоне. Поэтому тест полного восстановления честно эмулирует приближение камеры к непринятым областям того же листа. Это не режим ноутбука/слайд-шоу и не замена кодов на экране. Не заявлять «весь лист читается одним наведением». Номера оставшихся частей и инструкция направляют пользователя, когда весь лист слишком мелок. Автофокус/макро Safari не обещаются. Нужна физическая проверка iPhone с настоящим HTML.
